## 一、当前结论

网站的技术框架已经成型，静态构建和线上访问正常，但本地最新版尚未形成一个可以安全公开发布的版本。

当前主要问题已经不是“把网站做出来”，而是：

- 网站定位和销售路径不够聚焦；
- 首页由精选作品逐渐变成完整项目列表；
- 公开案例、待授权素材和内部资产索引混在同一套静态网站里；
- 本地内容远领先于线上部署；
- 新增内容完成了技术集成，但还没有完成全面视觉验收；
- 客户授权、署名和项目事实仍是公开发布的主要阻塞项。

因此，当前阶段更适合做一次内容与信息架构重构，而不是继续无筛选地增加项目。

## 七、当前主要问题

### 1. 首页不再是精选作品

首页目前会列出全部 30 个项目。项目数量继续增加后，首页会变成长目录，削弱：

- 第一印象；
- 核心能力识别；
- 重点客户关系；
- 视觉节奏；
- 联系转化路径。

需要决定首页应该展示多少项目，以及采用客户关系、行业、服务能力还是代表作品作为筛选标准。

### 2. 分类体系不够稳定

当前分类包括：

- Film + production
- Photography
- Food + menu
- Food + hospitality

Food + menu 与 Food + hospitality 的边界较弱；Photography 又与两个餐饮类别存在媒介层面的重叠。这套分类同时混用了媒介、行业和服务类型。

需要选择更稳定的分类维度，例如：

- 按服务：Film / Photography / Production
- 按客户需求：Campaigns / Events / Hospitality / Social
- 按行业：Automotive / Hospitality / Brand / Editorial
- 或使用一个主维度加辅助标签

### 3. 内部素材索引存在公开风险

本地 `/work/approved/` 页面包含：

- 71 个 Google Drive 项目文件夹名称；
- 客户记录；
- 项目类型；
- 直接 Drive 文件夹链接。

该页面没有身份验证，并且当前技术方案是纯静态网站。如果把本地最新版直接部署，这个内部索引会成为公开页面。

建议把内部素材管理与公开作品集彻底分离。静态公开站不应承担内部资产库功能。

### 4. 所有案例仍处于授权待确认状态

当前案例普遍缺少以下一项或多项：

- 公开展示授权；
- 客户关系确认；
- 项目日期与地点；
- 团队署名；
- 人物肖像授权；
- 品牌、音乐、第三方产品或场地授权；
- 医疗或治疗内容的合规确认；
- 可公开陈述的商业结果。

网站目前使用中性英文并显示 `Internal review` / `Publication clearance pending`，避免把未知信息写成事实。但公开网站长期显示这些提示，会削弱销售信任，也不能替代真实授权。

### 5. 新增餐饮页面缺少完整视觉 QA

新增内容已经完成素材选择、Web 衍生图和页面集成，也通过了构建测试。但 20 个新增餐饮案例尚未逐页完成：

- 桌面端检查；
- 手机端检查；
- 图片裁切与比例检查；
- 视频和图片加载检查；
- 页面长度与重复度检查；
- 浏览器控制台检查；
- 真实性与英文文案检查。

### 6. 生产环境配置没有收口

本地默认配置为：

- `NEXT_PUBLIC_SITE_URL=http://localhost:3000`
- `NEXT_PUBLIC_CONTACT_EMAIL=hello@cheese.studio`

线上旧版本的 Open Graph 域名正确，但本地最新构建若不带生产环境变量，会把社交图片地址写成 localhost。

### 7. 项目文档已经落后

README 和 handoff 仍描述九个左右的案例，而实际本地代码已有 30 个案例。部署压缩包、交接文档和实际源码并不同步。

### 8. 缺少 Git 基线

当前工作区没有 Git 提交，网站和其他工作室文件均处于未跟踪状态。重构前缺少可靠的版本比较和回滚点。

## 八、必须保留的约束

重构不能默认推翻以下既有决定：

- 网站可见文案保持英文，除非另行决定；
- 保留 First Rec. 品牌身份；
- 保留多页面结构；
- 保留暖调、编辑感、浅色视觉方向；
- 不加入自动深色模式；
- 保持静态导出和 NAS/Nginx 部署兼容；
- 不引入必须依赖服务端运行的功能；
- 保留无障碍和 reduced-motion 行为；
- 不使用滚动监听器或无必要的 JavaScript 动画；
- 不虚构客户评价、商业结果、项目日期、署名或授权；
- 不把文件夹名称或视觉判断当作已确认的商业事实；
- 优先继续使用 `app/_data/site.ts` 和共享 `CaseStudyPage`；
- 避免为每个项目制作不必要的独立组件。

## 九、重构时需要讨论的核心决策

### 定位

- First Rec. 的第一身份是 production studio、摄影摄像工作室，还是 Cheese 主导的灵活制作伙伴？
- 面向新客户时，最需要证明的是审美、执行能力、快速响应、成本控制还是跨语言协作？
- 活动与企业形象是否仍是主业务？如果是，网站是否被餐饮项目占据了过多注意力？

### 首页

- 首页精选项目数量应为 6、8、10，还是其他数量？
- 应优先展示知名品牌、视觉质量、服务范围还是长期客户关系？
- 是否需要明确的客户类型入口，例如 Brands / Hospitality / Events？
- 首页是否需要增加一个更明确的服务和联系转化段落？

### Work 页面

- Work 是精选案例页还是完整归档？
- 是否需要标签筛选，还是通过少量人工策展分组即可？
- 是否把 20 个餐饮项目合并成少数集合型案例，而不是每个品牌一个短页面？
- 是否保留单独的 Food + hospitality collection 页面？

### 案例页

- 一个可信的案例最少需要哪些事实？
- 缺少日期、角色和客户授权的项目是否应该只展示图片，不写“Challenge / Response / Outcome”？
- Film 项目、摄影项目和集合型餐饮项目是否需要不同模板？
- 是否需要显示具体 deliverables、角色、团队和渠道？

### 服务与设备

- Services 是否与目标客户的采购语言一致？
- Equipment Hire 是核心收入线、辅助服务还是内部能力证明？
- Equipment 是否应该留在主导航，还是降低到页脚或单独入口？

### 公开与内部边界

- 哪些内容允许出现在公开域名？
- 未授权案例是否应该完全不上线，而不是显示 pending 提示？
- 内部资产索引应迁移到哪里？
- 是否需要单独维护公开项目数据和内部项目数据？

## 十、可考虑的重构方向

以下只是讨论起点，不代表已经决定：

### 方向 A：强策展型销售网站

- 首页只展示 6–8 个最强案例；
- Work 保留 10–15 个公开案例；
- 其余内容不进入公开网站；
- 强调品牌、活动、企业和 hospitality 的综合制作能力；
- 最适合主动销售和建立高质量第一印象。

### 方向 B：行业入口型网站

- 首页按 Brand / Events / Hospitality 三类进入；
- 每类只展示少数代表案例；
- 用行业问题和交付方式解释服务；
- 适合客户类型差异较大，但需要避免内容被分散。

### 方向 C：能力入口型网站

- 首页按 Photography / Film / Production Support 组织；
- 项目可跨能力标签出现；
- 强调灵活团队和一站式执行；
- 适合突出制作能力，但可能弱化行业经验。

### 方向 D：精选案例 + 项目集合

- 重要客户保留独立深度案例；
- 大量短餐饮项目整合成 2–4 个主题集合；
- 例如 Menu & Product、Hospitality Spaces、Openings & Service；
- 可以降低页面碎片化和重复文案问题。
